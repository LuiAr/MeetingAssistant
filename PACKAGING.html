🔑 The one thing to get right

Everything else is mechanical. This is the part people trip on.

macOS grants privacy permissions (Microphone, Screen Recording) per app identity, keyed by the app's bundle identifier and its code signature. Your local development build and the public release are two different binaries. If they share the same bundle identifier, macOS treats them as the same app, and their permission grants and Launch Services entries fight each other. The fix is simple: give the release a different bundle identifier from your dev build.

In short Dev build stays devswift.MeetingAssistant (unchanged). The release gets a new, stable identifier you own, for example com.devswift.MeetingAssistant. Two identities, two independent permission grants, zero collisions.

🧰 Prerequisites

  • A Mac running macOS 15 (Sequoia) or later. The app's minimum target is now macOS 15.
  • Xcode 16+ or a matching Swift 6.2 toolchain (swift --version to check).
  • The project builds and tests cleanly first:
swift build
swift test
💡 Verify before you package The recent fixes were written without a local compiler available, so run swift build and swift test once and fix any errors before cutting a release. Everything else here assumes a clean build.
1

Choose your bundle IDs

Decide this once and keep it stable forever. Changing it later resets users' permissions.

BuildBundle identifierWhere it lives
Developmentdevswift.MeetingAssistantdist/ via build_and_run.sh
Official releasecom.devswift.MeetingAssistant/Applications after download

Use any reverse-DNS string you control for the release ID. Because the IDs differ, each shows up as its own row in System Settings ▸ Privacy & Security, with its own Microphone and Screen Recording switches.

⚠️ One resource is still shared Both builds save recordings to ~/Documents/MeetingAssistant Recordings (the path is hard-coded, not tied to the bundle ID). That is usually fine, but if you want full isolation, suffix the folder in debug builds. In RecordingStore.defaultRootDirectory: 
nonisolated public static var defaultRootDirectory: URL {
  let base = FileManager.default.urls(for: .documentDirectory, in: .userDomainMask)[0]
  #if DEBUG
  return base.appendingPathComponent("MeetingAssistant Recordings (Dev)", isDirectory: true)
  #else
  return base.appendingPathComponent("MeetingAssistant Recordings", isDirectory: true)
  #endif
}
2

Build a release app

A release build is optimised, and the development-only smoke-record mode is compiled out automatically.

The existing script/build_and_run.sh makes a debug bundle for local use. For a distributable build, save the script below as script/package_release.sh, make it executable (chmod +x), and run it. It mirrors the dev script but builds in release configuration and stamps the release bundle identifier.

#!/usr/bin/env bash
set -euo pipefail

APP_NAME="MeetingAssistant"
BUNDLE_ID="com.devswift.MeetingAssistant"
MIN_SYSTEM_VERSION="15.0"

ROOT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
DIST="$ROOT_DIR/dist"
APP="$DIST/$APP_NAME.app"

swift build -c release
BIN="$(swift build -c release --show-bin-path)/$APP_NAME"

rm -rf "$APP"
mkdir -p "$APP/Contents/MacOS" "$APP/Contents/Resources"
cp "$BIN" "$APP/Contents/MacOS/$APP_NAME"
chmod +x "$APP/Contents/MacOS/$APP_NAME"
cp "$ROOT_DIR/app.icns" "$APP/Contents/Resources/AppIcon.icns"

cat >"$APP/Contents/Info.plist" <<PLIST
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>CFBundleExecutable</key><string>$APP_NAME</string>
  <key>CFBundleIdentifier</key><string>$BUNDLE_ID</string>
  <key>CFBundleIconFile</key><string>AppIcon</string>
  <key>CFBundleName</key><string>$APP_NAME</string>
  <key>CFBundleShortVersionString</key><string>1.0.0</string>
  <key>CFBundleVersion</key><string>1</string>
  <key>CFBundlePackageType</key><string>APPL</string>
  <key>LSMinimumSystemVersion</key><string>$MIN_SYSTEM_VERSION</string>
  <key>NSPrincipalClass</key><string>NSApplication</string>
  <key>NSMicrophoneUsageDescription</key><string>MeetingAssistant records microphone audio so local transcripts can include what you say in meetings.</string>
  <key>NSScreenCaptureUsageDescription</key><string>MeetingAssistant captures system audio from meeting apps and browsers to transcribe remote participants.</string>
  <key>NSSystemAudioCaptureUsageDescription</key><string>MeetingAssistant captures system audio from meeting apps and browsers to transcribe remote participants.</string>
</dict>
</plist>
PLIST

codesign --force --sign - \
  --identifier "$BUNDLE_ID" \
  --requirements "=designated => identifier \"$BUNDLE_ID\"" \
  "$APP"

echo "Built $APP"
About signing --sign - is ad-hoc signing: no Apple Developer account, no notarisation. The app runs fine, but the first time a user opens it Gatekeeper will warn that it cannot be verified. Step 6 covers exactly how they get past that.
3

Package for release

A zip is the simplest. A DMG looks more polished. Either works for GitHub.

Option A - Zip (recommended, simplest)

Use ditto rather than the Finder's Compress, so the bundle's signature and symlinks survive intact:

ditto -c -k --sequesterRsrc --keepParent \
  dist/MeetingAssistant.app dist/MeetingAssistant-1.0.0.zip

Option B - DMG (drag-to-Applications feel)

hdiutil create -volname "MeetingAssistant" \
  -srcfolder dist/MeetingAssistant.app \
  -ov -format UDZO dist/MeetingAssistant-1.0.0.dmg

For a fancier DMG with a background image and an Applications shortcut, the create-dmg tool (brew install create-dmg) is worth a look, but it is optional.

4

Publish the GitHub Release

  1. Tag the commit: git tag v1.0.0 && git push origin v1.0.0.
  2. On GitHub, go to Releases ▸ Draft a new release, pick the tag v1.0.0.
  3. Write release notes. Tell users plainly that the app is unsigned / not notarised and link to the "first open" steps below.
  4. Attach MeetingAssistant-1.0.0.zip (and/or the DMG) as a binary asset.
  5. Publish.

Or do it from the terminal with the GitHub CLI:

gh release create v1.0.0 dist/MeetingAssistant-1.0.0.zip \
  --title "MeetingAssistant 1.0.0" \
  --notes "Local, on-device meeting transcription. Unsigned build - see the README for how to open it the first time."
💡 Include the notices Some dependencies are Apache-2.0, which asks you to keep their notices with redistributed binaries. Drop THIRD_PARTY_NOTICES.md into the release notes or alongside the asset.
5

The downloader's journey 🍎

What a user does after clicking your release asset. Walk through it yourself once.

  1. Download the .zip (or .dmg) from the release page.
  2. Unzip (double-click) or mount the DMG, then drag MeetingAssistant.app into /Applications.
  3. First open is blocked. Because the app is unsigned and downloaded, macOS quarantines it. On macOS Sequoia and later, the old Control-click ▸ Open trick no longer bypasses this. Use one of the two methods below.

Method 1 - System Settings (no Terminal)

  1. Double-click the app. You will see "MeetingAssistant cannot be opened because Apple cannot check it...". Click Done.
  2. Open System Settings ▸ Privacy & Security, scroll to the Security section near the bottom.
  3. Click Open Anyway next to the MeetingAssistant message, then authenticate.
  4. Launch it again and confirm. You only do this once.
⚠️ Time limit You must click Open Anyway within about an hour of the first blocked attempt, otherwise the button disappears and you start over.

Method 2 - Terminal (fastest, most reliable)

Strip the quarantine flag and the warning never appears. This also fixes the dreaded "app is damaged and can't be opened" message that quarantined unsigned apps sometimes show:

xattr -dr com.apple.quarantine /Applications/MeetingAssistant.app

Then open the app normally. Consider putting this exact command in your release notes for users who are comfortable with Terminal.

6

First run inside the app

  1. 🎙️ Download the model. Open Settings ▸ Models and download the Whisper model (about 1.6 GB, fetched from Hugging Face). Recording stays disabled until it is on disk.
  2. Grant permissions. Start a meeting; macOS prompts for Microphone and Screen Recording.
  3. Relaunch for Screen Recording. macOS only applies a fresh Screen Recording grant after a restart. The app detects this and shows Open Screen Recording Settings and Quit & Reopen buttons. Use them, then start again.
  4. Record. Talk, play some computer audio, stop, and confirm a transcript appears in the library.

🔀 Dev vs official, side by side

How the two builds stay out of each other's way once the IDs differ.

ConcernDev buildOfficial build
Bundle IDdevswift.MeetingAssistantcom.devswift.MeetingAssistant
Privacy permissionsOwn row in SettingsSeparate, independent row
Locationdist/MeetingAssistant.app/Applications/MeetingAssistant.app
Smoke-record modeAvailable (DEBUG)Compiled out
Recordings folderShared by default - isolate with the DEBUG tweak in Step 1 if you want them separate
💡 Make them visually distinct To tell the two apart at a glance (handy in the permissions list and the Dock), give the dev build a different display name. In script/build_and_run.sh, set CFBundleName to MeetingAssistant (Dev) in the generated Info.plist. The dev script already uses devswift.MeetingAssistant, so no ID change is needed there.

With different identifiers, you can keep the official app installed in /Applications and rebuild and run your dev copy from dist/ at the same time. Granting or revoking permission for one never touches the other.

✅ Test checklist

Tick these off on a clean machine (or a fresh user account) before you announce the release.

  • swift build and swift test both pass.
  • Release app launches from /Applications after the Gatekeeper bypass.
  • Microphone and Screen Recording prompts appear, and the Quit & Reopen flow works.
  • Model downloads in Settings, with progress and a Ready state.
  • A short recording produces a transcript with both "You" and "Computer audio" lines.
  • Pause / resume, mute, and Stop & Save all behave.
  • Stopping a recording mid-stream never crashes (this exercised the data-race fix).
  • Official and dev builds appear as two separate apps in Privacy & Security.
  • Release build does not respond to --smoke-record.
  • Quitting Wi-Fi mid-download shows "Waiting for internet" and recovers.

🛠️ Troubleshooting

"MeetingAssistant is damaged and can't be opened"

This is the quarantine flag on an unsigned download, not actual damage. Run xattr -dr com.apple.quarantine /Applications/MeetingAssistant.app and reopen.

Screen Recording is on but recording still fails

macOS needs a relaunch to apply the grant. Use the in-app Quit & Reopen button, or quit and reopen manually, then try again.

Permissions look granted but capture is silent

Almost always a bundle-ID clash from an earlier build that used the same identifier. Remove old grants in Privacy & Security, confirm the release uses its own identifier, and relaunch.

Model download fails or stalls

Check connectivity and free disk space (about 1.6 GB needed). The downloader retries with backoff and shows "Waiting for internet"; Cancel and Download again from Settings if needed.

Build error referencing ToolbarSpacer or an unavailable API

The minimum target is macOS 15. macOS 26-only APIs must stay inside if #available(macOS 26, *). If you add new SwiftUI that the SDK flags, gate it the same way.
